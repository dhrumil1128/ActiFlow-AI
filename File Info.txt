📁 File 1: agent/planner.py
🎯 Responsibility of this file

Take:

User task

Current system state (files, folders, etc.)

Ask Gemini to:

Think

Plan

Return structured JSON actions

No execution happens here

🧠 Key rule (important)

❗ This file ONLY plans.
❗ It NEVER touches the file system.
❗ It NEVER executes actions.

This separation is what makes your project safe and professional.



📁 File 2: schemas/action_schema.py
🎯 Responsibility of this file

This file defines what a valid action looks like in your system.

It acts as a contract between:

The AI planner (Gemini)

The execution layer (your code)

🔄 What this file takes

Raw action data generated by the LLM (JSON)

📤 What this file outputs

Validated, structured Python objects

Guarantees that:

Action names are allowed

Required fields exist

No unexpected or unsafe fields pass through

❌ What this file must NEVER do

❌ It must NOT execute actions

❌ It must NOT touch the file system

❌ It must NOT call Gemini or any LLM

🧠 Why this file is critical

LLMs are not trustworthy by default.

Even with a good prompt:

They can hallucinate fields

They can invent actions

They can return malformed JSON

This file is your first line of defense.

If an action fails validation here, it will never reach execution.

That’s what makes your agent safe and professional.

🧩 Design decision

We use Pydantic because:

Strong validation

Clear error messages

Easy to extend

Industry-standard for AI pipelines


📁 File 3: agent/validator.py
🎯 Responsibility of this file

This file is responsible for runtime safety checks.

Even if:

Gemini returns valid JSON

The schema validates correctly

…it does NOT mean the action is safe to execute.

This file decides:

“Is this allowed to run in THIS environment?”

🔄 What this file takes

A validated Plan (from action_schema.py)

Current runtime context (base directory, permissions)

📤 What this file outputs

A filtered and approved list of actions

Or raises an error if something is unsafe

❌ What this file must NEVER do

❌ It must NOT execute actions

❌ It must NOT modify files or folders

❌ It must NOT call Gemini or any LLM

🧠 Why this file is critical

This is your second safety layer.

Think of it like:

action_schema.py → “Is the structure valid?”

validator.py → “Is this action safe to perform here?”

Even a perfectly structured action can still be dangerous:

Deleting files

Moving files outside the project

Renaming system files

This file prevents that.

🧩 Design rules we enforce here

Actions must stay inside a base directory

No absolute paths allowed

No directory traversal (..)

Destructive actions must be blocked

no_action is always safe


📁 File 4: agent/executor.py
🎯 Responsibility of this file

This file is responsible for executing approved actions.

At this point:

The plan is created ✅

The schema is validated ✅

The actions are safety-checked ✅

This file simply does what it is told, nothing more.

Think of it as the hands, not the brain.

🔄 What this file takes

A list of approved Action objects

Actions that are already:

Structurally valid

Safety validated

📤 What this file outputs

Executes the actions on the file system

Returns execution results (success / failure)

Produces predictable, deterministic behavior

❌ What this file must NEVER do

❌ It must NOT talk to Gemini

❌ It must NOT decide what to do

❌ It must NOT validate safety rules

❌ It must NOT generate plans

If something is unsafe, it should have already been blocked before reaching this file.

🧠 Why this separation matters

This separation ensures:

The executor is boring and predictable

Bugs here don’t lead to dangerous decisions

You can audit execution logic independently

This matches real-world production systems

This is exactly how enterprise automation engines are designed.

🧩 Design rules here

One action = one function

No hidden logic

No assumptions

Fail loudly if something unexpected happens

🎯 Responsibility of this file

This file is the orchestrator of the entire system.

It connects all the pieces you’ve built so far and runs the agent loop end-to-end.

Think of it as the conductor of an orchestra:

Validator checks safety

Executor acts

Controller coordinates everything

🔄 What this file takes

Base directory (scope of allowed actions)

📤 What this file outputs

Executes a complete agent cycle:

Planning

Validation

Execution

Returns:

The final plan

The actions taken

Any errors (if blocked)

❌ What this file must NEVER do

❌ It must NOT directly call file system APIs

❌ It must NOT embed safety logic

❌ It must NOT generate AI prompts itself

❌ It must NOT bypass validation

This file coordinates, it does not decide or execute.

🧠 Why this file is critical

This file proves your project is:

Not a script

Not a demo

A real agent architecture

It clearly shows:

Observe → Plan → Validate → Act

This is the exact pattern used in enterprise automation, AIOps, and robotics control systems.

   ↓

📁 File: schemas/plan_schema.py
🎯 Responsibility of this file

This file defines what a complete AI plan looks like.

It represents the full output of the AI planner, not just individual actions.

Think of it as:

The contract for “what a valid plan means” in ActiFlow AI.

Raw plan data returned by the AI planner (after JSON parsing)

📤 What this file outputs

A validated Plan object containing:

A high-level intent summary

❌ It must NOT execute actions

❌ It must NOT perform safety checks

❌ It must NOT call Gemini or any AI

Cleaner schema design

Professional, scalable architecture

In real systems, plans and actions are never mixed.
